# Adopting an earlier project

Use when setup encounters earlier Atlas formats, customized homes, or another task authority. Inspect the actual project before changing it. The format-3 templates are the candidate contract, not permission to discard existing conventions.

For local Atlas format 2, preserve content and historical ids. Record each part's old heading-derived id explicitly before a display rename or move. Retain briefs, task numbers, canceled work, deliveries, reviews, and human checks. Update owned format guidance and instruction pointers while preserving custom additions. Matching task status no longer establishes handoff freshness; newer work uses output-and-scope evidence. Old evidence is not backfilled as if it had been observed: rerun only the checks needed for a new use or changed scope.

Before replacing adopted scope or accepted output that cannot be recovered through existing storage, keep a dated copy or versioned artifact and link it. Keep old historical notes unchanged. Inspect incoming dependencies after changing any work identity or canceling tasks.

For existing CONTEXT.md or another domain glossary, select one authoritative home and use a pointer from GLOSSARY.md when that preserves the project's convention. Merge duplicate terms only after resolving meaningful conflicts. The same principle applies to an existing map or work directory: a pointer may adopt it, but the current plan must have one task authority.

Hosted-task projects require an explicit migration scope. Inventory old ids, states, blockers, output locations, outstanding human judgments, and project policy. Retain old-to-new links and reasons for state conversions; reconcile missing evidence instead of inferring acceptance from closed issues. Until that mapping and the resulting local work are verified, preserve the old authority and name the pending migration. Ordinary setup does not silently convert it.

Before finishing, verify links, unique owners, dependency validity, the preserved content, and how a fresh session resumes. A partial migration records completed changes and its next unresolved action; repeating setup continues that action and does not duplicate homes or instruction blocks.
