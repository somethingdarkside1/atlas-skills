# Map it

Keep the project's responsibilities and navigation understandable.

Read the current map format, selected sections and split-file pointers, affected briefs/tasks/decisions, and project instructions. The map format owns ids and views; the plan format owns work and acceptance.

1. Establish whether the request is a redraw/link repair, a move of existing sections, or a change in responsibilities. Redraw and move existing information directly within the request. For a consequential scope choice, use [interviewing](interview.md) and record the decision before redistributing work.
2. Verify unique stable part ids, resolvable references, valid decision prerequisites, and cycles across detail files. Follow inbound references when an identity or location changes. Report uncertain relationships for their actual owner; a redraw supplies no missing decision or accepted outcome.
3. Keep one full authoritative section per part. Split the presentation when navigation becomes difficult, preserving ids, task paths, and labeled pointers. When responsibilities really change, retain history and assign ownership for every existing brief, task, and dependency before calling the change complete. A display rename preserves the stable id.
4. Generate the diagram from the authoritative sections in a legible layout. Keep task blockers in the plan. Reconcile status with actual adopted scope and acceptance: a redraw can reopen a stale done label, but it cannot create combined Outcome acceptance from task counts. Link the required review or known missing work.

Save only the owned map files and links that changed, under project policy. Report the structural change or specific unresolved fault and its next action. If the map is already consistent, say so without rewriting it or inventing another task.
