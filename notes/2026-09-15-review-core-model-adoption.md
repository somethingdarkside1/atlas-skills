### GitHub boundary

A thin project convention can identify an issue as a coordination reference, a PR as a proposed change, a specific head revision as an artifact reference, and a verified merge result as integration evidence. These are relations, not equivalences: an issue can coordinate a package with many tasks, and a PR can contain several outputs or successive attempts. A PR URL alone does not identify the reviewed content, and neither issue closure nor PR approval substitutes for the task's evidence.

GitHub explicitly allows [issue closure for work that is not planned](https://docs.github.com/en/issues/tracking-your-work-with-issues/administering-issues/closing-an-issue). Its [merge documentation](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/merging-a-pull-request) describes integration into a branch under repository requirements. These sources support retaining the distinction between external status and Atlas acceptance.

The first release requires no GitHub task adapter. A later adapter would translate storage and preserve identity, evidence, dependencies, and recovery while core acceptance semantics stay the same. Source hosting, issue coordination, and authorized PR delivery remain usable now under project instructions. Legacy GitHub task projects retain their authority until an explicit supported migration or receive a truthful unsupported notice; task 03 owns that path.
