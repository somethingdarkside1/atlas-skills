01

Why a second pass, and what it was for

The first pass listed nineteen seams: rules stated twice with small differences, states one skill wrote and another could not read, and words the glossary bans that the skills then used. The second pass asked a different question of each seam: not "which text is right" but "why were there two texts at all". Three answers covered nearly everything.

A rule had no home

"Which task is next" and "what is a task called" were never written anywhere as rules, so each skill that needed one improvised, and improvised differently. Now each has one home and skills point at it.

A wait lived in chat

Review waited for the human's word, build looped when it needed an answer, and nothing on disk said a task was waiting. A parked session or /atlas go could not tell. Waits now leave a state on disk.

Git was told in five places

The tracker paragraph, decision 0007, each skill's commit step, and the branch rule in build-it each described part of the same story. It is now one section, read by every skill through one sentence.

The rule under the rules
Every rule has exactly one home, a skill points at the home instead of quoting it, and when a skill and a home disagree the home wins. This is decision 0011, and it is now in the block /atlas writes into every project's CLAUDE.md.

03

How the agent stays unconfused

An agent reading two texts that disagree does one of three things: picks the first, picks the most specific, or averages them. All three are wrong some of the time. The set now removes the choice rather than guiding it.

  • One home, and a tie-break. The block in every project's CLAUDE.md says the format wins over the skill. An agent that finds a conflict has an instruction for that case, and the instruction also names what to fix.
  • The same sentence in the same place. Every skill opens with the identical step 1, commits with the identical sentence, and ends with an identical last-line shape. When eight skills say one thing eight ways, the agent infers eight rules. When they say it one way, it infers one.
  • Status is derived, never asserted. Sketched means no brief. Decided means a brief and every task still todo. Building means at least one task past todo and not all done. Done means all tasks done. A skill and a person reading the same folder reach the same status without trusting a line that may be stale; /atlas repairs the line to match.
  • Waits are visible. A task in review with an unticked (you) box, an open question on the map written by /build-it, a live handoff: each is a file state the next run reads. Only rounds and the prototype verdict wait in chat, and the skills README says so, so an agent knows those are the exceptions rather than a pattern to copy.
  • Negatives only as boundaries. The old rule "positive instructions only" was broken in every skill, which taught the agent the rule was soft. The new rule is honest: positive by default, one boundary per step where a positive cannot draw it. Most old negatives became positives ("leave the brief, the other tasks, and the rest of the map as they are").
  • Formats are pointed at, not paraphrased. /map-it no longer restates the diagram spec; it says "exactly as the format comment says". A paraphrase is a second copy that drifts.
  • The glossary's Avoid lists are enforced on the skills themselves. Four banned words (frontier, batch, pass, turn) were in the skills. Two were reworded, one became a real term (Pass), and a grep now shows none.
04

Git, GitHub, and no git at all

Three environments. The whole difference is written once, in the Git section of plan/README.md, and every skill's commit step is the one sentence "Commit as plan/README.md says". Decision 0007 (branches only with GitHub) stands and now has one place to be true.

EnvironmentCommitsBranches and PRsWho pushes
No repoNone. Skills write files. /atlas offers git init and reports no repo on line four until then.NoneNobody
A repo (Tracker: files)Each skill commits what it wrote, on the branch that is checked out, as <skill> <id>: <what>. A rejected hook prints one line and stops. /park-it commits the five things and prototypes/ wholesale.None. Work happens in place.You. Skills push nothing.
A repo with Tracker: githubAs above for every skill except /build-it, which commits on its task branch./build-it: clean tree, branch part/NN-slug from the default branch, push, PR with Closes #NN, then back to the default branch. /review-it: squash-merge and delete (Merge: review-it) or mark ready (Merge: human), then pull the default branch.Skills push only the PR branch. You push the default branch.

Two things this fixes that would have bitten on the first GitHub run: nobody returned to the default branch after opening a PR, so the next interview would have committed onto a task branch that review-it then deleted; and /build-it committed the task file but not the map it had just edited, so /atlas reported its own work as a problem.

Two things left as they were, on purpose: the Merge: line stays in the file even with files, where it is ignored, so the format is one shape everywhere; and /atlas asks the tracker and merge questions together in one round only when a GitHub remote exists, so a plain folder gets no question at all.

05

The loop as it runs now

Task statuses drive the loop. Every arrow is a status change owned by exactly one skill, and /atlas reads the statuses to choose the next command.

sketched · no brief decided · brief, every task todo building · a task past todo, not all done done · every task done 
flowchart LR
  todo -- "build-it picks it" --> doing
  doing -- "Delivered written" --> review
  review -- "findings" --> doing
  review -- "clean (and merged)" --> done
  doing -- "brief silent: question to the map" --> interview["interview-me"]
  interview -- "brief rewritten" --> doing

Where /atlas go stops, by design: at any command other than build or review, at a task with three passes carrying findings, and at a review that lists boxes only a person can tick. Each stop is a state on disk plus a Next: line, so the next session starts where this one ended.

07

Found on the second read, not the first

  • The invocation flag and go. Every skill carries disable-model-invocation: true, so /atlas go could never invoke build-it as a skill. Both install paths (skills.sh, the plugin, the link script) place skills as sibling folders, so following ../build-it/SKILL.md as a file is portable and keeps the flag.
  • Project-scope interviews were writing decisions. Step 6 applied to both scopes while step 4 and decision 0005 said the project scope decides nothing. Now scoped.
  • The Plan: line had two owners. Interview set it, plan-it and atlas tested it as "no plan yet". Now interview sets it to the brief, plan-it to the folder, and "has a plan" means "has a task".
  • Splitting a decided part lost its status. Sub-parts start sketched, so the derived status fell back. Documented, with the advice to split early.
  • Nothing removed an (answered) question. Interview-me now copies the verdict into a decision or the brief and removes the line, so the part can reach none.
  • Proposed decisions were never revisited. A re-interview now asks about them first.
  • Two note kinds had no writer. The notes README now says research and review notes are written by hand or by whatever agent did the work.
  • The example broke decision 0004. Its three folder READMEs were stubs pointing at the Atlas README. They now carry the formats, task 01's pass is dated, (you) boxes are marked, and Palette's questions are a list.
  • "Seven to nine parts" read as a floor. The example has two. Now "at most nine".
08

What else is needed

In order, because each step tells you whether the next is worth taking.

  1. The end-to-end test in files mode. Copy examples/brand/ to a scratch folder, git init, then /atlas, /interview-me palette, /plan-it palette, /build-it, /review-it, /atlas go, /park-it, /atlas, then /prototype-it on a (prototype) question and /map-it palette for a split. Record what broke as one review note and fix the skill.
  2. The same in GitHub mode on a real repo. This is also the check that gh 2.100 can create sub-issues and blocked-by dependencies from the command line; if it cannot, the tracker paragraph needs a fallback (labels and a "blocked by #n" line in the body) and that is a decision.
  3. A mechanical checker. A small scripts/check.sh that tests unique part ids, blockers that exist, headings that match diagram nodes, and node classes that match status lines. /atlas line four then rests on a script's output rather than a read, and a pre-commit hook can run it.
  4. Packaging. scripts/link-skills.sh, claude plugin validate . --strict, and a check that skills.sh installs the eight as siblings (the go rule depends on it). Then the README's install section, the blog post, and the push.
  5. Two small decisions to take while testing. Whether a task branch is deleted by the human under Merge: human or by a GitHub setting; and whether /review-it under Merge: human should pull the default branch after the person merges, or leave that to the next /atlas.
  6. Open for the reviewer. When /build-it stops on a silent brief under a GitHub tracker, it is on the task branch, so the open question it writes to the map lands there. Either commit that map edit on the default branch or accept it riding the PR; the handoff note asks for a call.
  7. The map's own statuses. All seven skill parts on MAP.md read building until the test passes. That is honest; move each to done as its run comes back clean.
